# mmap Desktop — Implementation Plan

Source of truth: [`docs/PRD-desktop`](./PRD-desktop) (v2.0, 2026-10-26). This plan turns the PRD's
phased delivery table (§12) into concrete, reviewable increments. Each phase ends with its PRD
exit criteria verified by automated tests where possible and a short manual checklist otherwise.

## 1. Requirement review — key observations

| Area                                           | Observation                                                                                                                               | Consequence for the plan                                                                                                                                                                                                  |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage identity                               | One workspace = one folder = one SQLite file, yet the logical model carries `workspace_id` everywhere.                                    | Keep `workspace_id` columns and enforce them with composite foreign keys `(workspace_id, id)`. Cross-workspace links become impossible at the constraint level, and the schema stays server-ready.                        |
| Relationships vs. references vs. map structure | Three distinct concepts that users will confuse (§4.2–4.4, §14).                                                                          | Three separate tables (`relationships`, `note_references`, `map_connections` / placement parent) and separate domain modules. Nothing creates one from another implicitly.                                                |
| Undirected duplicates                          | Must use canonical endpoint ordering.                                                                                                     | Domain rule normalizes ordering, and a CHECK constraint rejects non-canonical undirected rows as a second line of defense.                                                                                                |
| Type directionality                            | Cannot change while used.                                                                                                                 | Relationships copy the type's directionality into a composite FK, so the DB blocks the change. Phase 2 adds the service check and requires a new type instead of a migration flow.                                        |
| Native dependencies                            | The build machine has no C++ toolchain; `better-sqlite3@13.0.3` has **no** Electron 44 Windows prebuild (verified: HTTP 404 for ABI 149). | Use the SQLite engine built into Node (`node:sqlite`) — no native build, same engine (SQLite 3.53.4, FTS5, online backup API) in Node 24 tests and inside Electron 44. Recorded in ADR-0002.                              |
| Testing vs. runtime parity                     | Tests run on system Node 24.21, app runs on Electron's Node 24.22.                                                                        | Same SQLite version in both (verified). CI additionally runs a packaged-app smoke test that exercises migrations inside Electron.                                                                                         |
| Security                                       | Electron hardening, narrow IPC, sanitized notes, safe archives (§8, §11).                                                                 | Built into Phase 0 shell (not retrofitted): sandbox, context isolation, CSP, custom `app://` protocol, navigation/window denial, sender validation, schema-validated IPC. Later phases add their own hostile-input tests. |
| Signing                                        | Signed installer + verified updates required for release.                                                                                 | Phase 0 packages unsigned NSIS builds; signing/update pipeline is a Phase 5 release gate (ADR-0004).                                                                                                                      |
| Offline / no CDN                               | Fonts, KaTeX, editor assets must be bundled.                                                                                              | CSP forbids remote origins; Vite bundles all assets.                                                                                                                                                                      |

### Ambiguities resolved by default (revisit if wrong)

1. **Package manager:** npm workspaces (bundled with Node; no extra global install).
2. **Electron line:** 44.x (current stable minus one; 45.0.0 is days old). ADR-0003.
3. **TypeScript:** 6.0.x, because `typescript-eslint` does not yet support TypeScript 7.
4. **Migrations:** ordered TypeScript modules exporting SQL text, so they bundle into the main process without loose files.
5. **Undirected relationship ordering:** lexicographic order of node UUIDs (`source_id < target_id`).

## 2. Repository layout

```
apps/desktop/                 Electron app (electron-vite)
  src/main/                   main process: window, security, IPC handlers, composition root
  src/preload/                minimal typed bridge (contextBridge)
  src/renderer/               React + Tailwind + shadcn/ui
packages/domain/              pure TypeScript domain rules + ports (no Electron/React/SQLite)
packages/contracts/           IPC channel catalogue, DTO schemas (zod), error codes
packages/storage-sqlite/      node:sqlite adapter: connection, migrations, repositories
docs/                         PRD, plan, architecture, ADRs, runbooks
```

The dependency direction is `apps/desktop → storage-sqlite → domain` and `apps/desktop → contracts → domain`.
`domain` imports nothing infrastructural. ESLint rules plus an architecture test enforce this.

## 3. Phases

### Phase 0 — Foundation (done)

Deliverables

- Monorepo with strict TypeScript, ESLint, Prettier, Vitest, lockfile, pinned versions.
- `domain`: IDs, clock, error model, repository/transaction/search/attachment-store ports.
- `contracts`: typed IPC catalogue with runtime validation, error envelope.
- `storage-sqlite`: connection factory (foreign keys, WAL, busy timeout), migration runner
  (transactional, refuses newer schemas), full initial schema for the logical data model
  incl. FTS5, integrity triggers.
- `apps/desktop`: hardened Electron shell, `app://` protocol, CSP, sender-validated IPC,
  React shell with the five main navigation areas, diagnostics view, `--smoke-test` mode.
- Packaging: electron-builder NSIS x64 (unsigned), packaged smoke test.
- CI (GitHub Actions, Windows): format, lint, typecheck, unit/integration tests, build,
  package, packaged smoke test, dependency audit, secret scan.
- Docs: README, local setup, architecture overview, ADRs required by PRD §14.

Exit criteria: clean `npm ci && npm run verify` works; packaged app launches offline;
migrations/builds pass.

### Phase 1 — Private knowledge base

Workspace lifecycle (create/open/rename/switch, manifest, process lock with stale recovery,
missing-folder handling, verified move), node CRUD with revisions and autosave states,
Tiptap editor with KaTeX (bundled), validated versioned note JSON + derived plain text,
tags, managed attachments (staging, checksums, reconciliation, traversal/symlink protection),
note sanitization tests. Exit: workspace isolation, content survives restart, offline.
Merged into `main`; see [§6](#6-phase-1-status-2026-10-26) for what was done and what was not.

### Phase 2 — Connections and discovery

Relationship types (seeded defaults, custom, archive), relationship CRUD with direction and
uniqueness rules, wikilink picker and reference reconciliation in the note-save transaction,
backlinks with excerpts, unresolved-link repair, FTS5 search with title boosting, snippets,
filters, pagination; search benchmark harness on the PRD dataset.
Merged into `main`; see [§7](#7-phase-2-status-2026-10-27).

### Phase 3 — Mind maps

Map CRUD/duplicate, placements of canonical nodes, React Flow freeform mode, hierarchical
mode with deterministic layout, cycle rejection, reviewed freeform→hierarchy conversion,
viewport/coordinates persistence, map revisions, keyboard alternatives.
Merged into `main`; see [§8](#8-phase-3-status-2026-10-27).

### Phase 4 — Graph and timeline

Cytoscape graph with bounded neighborhood loading, visible partial-result indicators, filters,
optional note-reference layer, accessible list alternative; timeline events with editing-session
grouping (30 min inactivity), reviewed/reflection events, timezone display. Extended within the
phase into a visual timeline with learning milestones and user-set learning dates.
Implemented on branch `phase-4-graph-timeline`; see [§9](#9-phase-4-status-2026-10-27).

### Phase 5 — Portability and release

ZIP export/import (validation, limits, traversal protection, ID mapping, duplicate warning,
transactional apply), Markdown export, SQLite-backup-based snapshots with retention and restore,
signed installer and update verification, accessibility pass, security test suite, complete
documentation, performance verification on the reference machine.
Partly implemented on branch `phase-5-portability`: export, import, backups, restore, the
automated accessibility check and the signing configuration are done; the signed release,
automatic updates, clean-machine and reference-machine verification are not. See
[§10](#10-phase-5-status-2026-10-27).

## 4. Cross-cutting rules applied in every phase

- Every bug fix ships with a regression test.
- SQLite behaviour is tested against real temporary databases, never mocks.
- New IPC channels require: contract schema, sender validation, handler test, and a doc entry.
- Comments explain intent, invariants and security decisions in English.
- Consequential decisions get a short ADR in `docs/adr/`.

### Not yet done in Phase 1

PRD §5.1 and §5.2 items that are **not** implemented:

- **Multiple app windows** (PRD §5.1). The app has a single window. Revision checks are in place
  and reject stale writes, so a second window can be added on top of the same services.
- **Timeline UI.** Events are recorded; the Timeline view is Phase 4.
- **Search UI.** The FTS5 index is maintained on every save; search and title lookup are Phase 2.
- **Opening a node from search, graph, timeline, map or backlink** (PRD §5.2). Only the Library
  opens nodes; the other entry points arrive with their views.

Other gaps found while checking the code:

- **Worker thread for heavy database work** (carried from Phase 0). Not done: all SQLite and file
  work runs on the main process thread. Phase 1 workloads are small; revisit before imports,
  exports and layouts.
- **Delete preview counts for relationships and referencing notes are always 0** until Phase 2
  writes those tables.
- **No test drives the real UI with clicks.** The packaged smoke test exercises the bridge, the
  attachment store, the preview protocol and the CSP inside the real app, but not the React
  components or native dialogs.
- **Accessibility pass** (PRD §6, §11): components use labels, roles and keyboard-reachable
  controls, but no structured accessibility check has been run (Phase 5).

### Not yet done in Phase 2

- **Search target not confirmed on the reference machine.** The benchmark ran on a developer
  machine, on system Node, calling the index directly (no IPC, no renderer), with rows inserted by
  SQL. PRD §9 requires the installed release on the documented four-core, 16 GB, SSD computer.
  That measurement belongs to the Phase 5 performance pass. The benchmark is not run in CI.
- **"Ambiguous title requires selection" applies only to the picker.** There is no Markdown or
  raw-text import yet, so no code resolves `[[Title]]` text. Every link is made by choosing one
  node in the picker, so ambiguity cannot arise today. Import (Phase 5) needs its own resolution
  step that asks the user.
- **Changing the text of an existing link.** New links can get custom text (`[[target|label]]`
  via the "Link text" field); to change it later, delete the link and insert it again.
- **Hebrew niqqud.** Pointed and unpointed Hebrew words do not match each other in search (a
  tokenizer limitation, documented and tested). Fixing it needs custom normalization of indexed
  and query text.
- **Offset-based search paging.** Editing nodes between "Load more" requests can repeat or skip a
  result; ranked results have no stable keyset.
- **Picker case and accent folding.** Title lookup folds ASCII case only and does not ignore
  accents, unlike full-text search, because `node:sqlite` has no ICU.
- **Relationship-type filters in search** (PRD §5.8, "where applicable") were not implemented
  (added after Phase 5, section 14). Creating relationships from a graph action (PRD §5.5) waited
  for the Phase 4 graph (added after Phase 5, section 13).
- **No UI tests** for the picker, relationship form, types dialog, backlinks or search view, and no
  structured accessibility check of them (Phase 5).
- **Worker thread** (carried from Phases 0 and 1). Search and all other database work still run on
  the main process thread.

### Not yet done in Phase 3

- **No drag-to-reparent on the canvas.** In hierarchical mode items cannot be dragged at all,
  because the layout computes their position. The hierarchy changes only in the outline (buttons
  or Alt+arrow keys), one step at a time: up, down, indent under the previous sibling, outdent.
  Moving an item under a distant parent takes several steps; there is no "move to…" picker.
- **Connectors cannot be drawn in hierarchical mode.** Existing connectors are shown and can be
  deleted, but new ones can be drawn only in freeform mode.
- **Relationship links on connectors have no UI.** The service and `maps:add-connection` accept
  a `relationshipId` (checked to connect the same two nodes), but the canvas always creates a
  plain connector. Linking a connector to a relationship (PRD §4.4) therefore exists only in the
  API. (Connector labels got a UI and `maps:set-connection-label` after Phase 5.)
- **The switch-to-hierarchy review offers limited choices.** For each item the dialog offers only
  the proposed parent (or the candidates of an ambiguous item) and "Top level". Any other parent
  has to be set afterwards in the outline.
- **Map list.** No search, filter or sort options; maps are listed by their last structural change
  (viewport changes do not count). Maps are renamed from the list, not from the editor.
- **One placement per node per map.** A node appears at most once on a map (the PRD version 1
  rule, enforced by the service and a unique constraint).
- **Six colors.** Placement styling is limited to six named colors (`gray`, `blue`, `green`,
  `amber`, `red`, `violet`) or the default. Connectors have no styling, although

### Not yet done in Phase 4

- **Regions are drawn for at most 12 maps at once**, and region outlines are convex: a map whose
  members are far apart gets a large outline that can include unrelated nodes in between (they are
  not members; badges, the tooltip and the side panel say which maps a node is on).
- **Collapsed maps are not remembered** between visits to the Knowledge Graph.
- **No drag-to-connect** in the graph. (Creating relationships from the graph, PRD §5.5 "or
  graph action", was added after Phase 5: see section 13.)
- **The canvas is not keyboard-operable.** Cytoscape draws on a canvas element that has no
  focusable nodes. The List tab is the accessible alternative and offers the same actions (open,
  focus, expand); the toolbar, filters and side panel are ordinary controls.
- **Rearrange replaces manual positions** of every visible node; there is no undo. Nodes hidden
  by Focus mode keep their positions.
- **The automatic first layout is limited to 300 nodes.** Larger graphs opened without saved
  positions keep the overlap-free stable placement (rows below and around placed neighbors) until
  the user clicks Rearrange.
- **Map colors repeat after 8 maps** (`MAP_COLORS`), and a node shows at most 6 map slices plus
  one neutral slice. Names in the tooltip, side panel and List tell maps apart.
- **Labels of parallel edges can overlap.** Several relationships between the same two nodes are
  drawn as separate curves, but their labels can cover each other; the side panel and the List
  name each one.
- **Expansions cannot be cleared.** Expanded neighborhoods are re-applied after reloads and filter
  changes (while the expanded node is still in the overview); only leaving the Knowledge Graph
  screen removes them.
- **No overall cap after expansions.** The overview is capped at 1,000 nodes, and each expansion
  adds up to 200 neighbors, but the merged view has no total limit; many expansions can put more
  than 1,000 nodes on the canvas.
- **Position saves are fire-and-forget.** A failed `graph:save-positions` call is not reported;
  the node then returns to its last saved (or newly placed) position on the next visit.
- **Search has no relationship-type filter** (PRD §5.8, carried from Phase 2). Added after Phase
  5 (section 14).
- **No import marking yet.** `is_imported` and `import_origin` exist and the timeline shows an
  "Imported" badge for such events, but nothing creates them until import arrives in Phase 5.
- **Sessions are placed at their start time.** An editing session is ordered, grouped by day and
  matched by date filters and by the visible window by its effective time: its start
  (`occurred_at`), or its learning date when one is set (it is then drawn as a point, not a span).
  A session that ran past midnight appears in the List only under the day it started, and one
  that started before the "From" date or the visible period is not shown even if it continued
  into it.
- **No tag or topic lanes.** The visual timeline is a single axis; lanes per tag or topic are a
  planned later enhancement.
- **Relationship events name the source node only.** A `relationship_created` event records the
  source node and its title (the timeline says "Added a relationship from …"), not the target or
  the type, and it is not updated when the relationship is reversed or deleted.
- **Tag filters use current tags.** The timeline's tag filter matches nodes that carry the tags
  now, not when the event happened; events of deleted nodes never match a tag or node filter.
- **No UI tests and no screen-reader pass.** `graph-model.ts`, `timeline-model.ts` and
  `timeline-axis.ts` are unit-tested. The packaged smoke checks open the graph and timeline views,
  and the timeline check sets two type filters and the Day zoom, finds markers on the axis and
  opens the event panel, but no test drives the graph filters, either List tab, panning and
  zooming by drag or wheel, the review and milestone dialogs, editing in the event panel or the
  timezone setting. Screen-reader and WCAG checks are Phase 5.
- **Performance only partly measured.** Both measurements ran on a developer machine; the
  reference machine with the installed build belongs to the Phase 5 performance pass.
- **Worker thread** (carried from Phases 0 to 3). Graph queries run on the main process thread;
  the Cytoscape layout runs on the renderer's main thread.
- **Export of timeline records** arrives with ZIP export in Phase 5.

### Not yet done in Phase 5

- **Signed installer.** Signing is configured, but there is no certificate. Current builds are
  unsigned, and release is blocked until `verify-signature.ps1` passes on the release build.
- **Automatic updates.** electron-updater with signature verification, and update checks that are
  visible in Settings and can be turned off, are not implemented, because no update feed host has
  been chosen. Updates are manual: running a newer installer keeps all data.
- **Clean-machine verification.** Install, offline launch, upgrade and uninstall with data
  preserved have not been verified on a clean Windows machine or virtual machine.
- **Reference-machine performance.** All measurements above are developer-machine numbers (system
  Node or the unpacked build), not the installed build on the documented four-core, 16 GB, SSD
  computer.
- **Worker thread** (carried from Phases 0 to 4). Large imports ran on the main process thread
  (importing 10,000 nodes kept the app busy for about 8 seconds). Done after Phase 5: import
  writes run in a worker thread (see section 12).
- **Accessibility.** Only automated checks have run. A manual keyboard and screen-reader pass is
  still needed, and the graph canvas itself is not keyboard-operable (the List tab is the
  alternative).
- **Import always adds copies.** There is no merge or update of existing records. Duplicate
  detection uses the export ID, so a new export of the same data is not recognised as a
  duplicate.
- **No progress bar or cancel** for long exports, imports or backups; the UI shows a busy message
  only. `transfer_jobs` records only completed imports, not exports, backups or failed jobs.
- **Backup destinations on network shares are not refused** (only workspaces are).
- **Markdown export** leaves out maps and timeline history by design, and cannot be imported.

## 12. Import writes in a worker thread (2026-10-28)

PRD §9: "Keep the UI responsive with workers." The records of a ZIP import are written in a worker
thread (`apps/desktop/src/main/workers/import-worker.ts`, `portability/import-writer.ts`) while
the main process holds the workspace's write queue (`SqliteConnections.runExclusive`, new). The
worker has its own connection and runs the same `ImportService.apply` transaction, so the
all-or-nothing guarantee is unchanged.

| Measurement (packaged app, 5,000 nodes) | Main thread before | Worker |
| --------------------------------------- | ------------------ | ------ |
| Import apply, total                     | 3.8 s              | 4.2 s  |
| Longest stall of the main process       | 3.8 s              | 19 ms  |

Tests: `sqlite-connections.test.ts` (runExclusive: another connection writes while transactions
wait; failures release the queue; refused inside a transaction), `round-trip.test.ts` (the full
round trip also through a separate connection with a structured-cloned job; a failure part-way
leaves nothing and the workspace stays writable), `import-writer.test.ts` (errors across the
thread boundary). The packaged smoke check "workspace exported to ZIP and imported back" imports
through the real worker. Still on the main thread: export, backups and restore (on the 10,000-node
dataset a whole export took 0.9 s, a backup 1.6 s and a restore 2.7 s; only part of that blocks),
search and graph queries.

## 13. Relationships from the knowledge graph (2026-10-28)

PRD §5.5: "Users can create relationships from a node detail panel or graph action." The graph's
side panel has **Add relationship**, which opens the node panel's form for the selected node.
While it is open, clicking another node on the canvas, or choosing it with **Find**, makes it the
other end without changing the selection; the form's picker works from the keyboard. The new edge
appears as soon as the relationship is saved.

Packaged smoke check "a relationship is added from the knowledge graph (Find and a click on the
node)": selects a node with Find, opens the form, chooses the other node with Find, clears it,
chooses it again with a real mouse click at the position Cytoscape reports (its instance is
registered on the container as `_cyreg`), checks that the selection did not move, saves, and
finds the relationship. The packaged smoke run now has 20 checks and a 240-second limit (the
previous 120 seconds were reached once on a busy machine).

## 14. Relationship-type filter in search (2026-10-28)

PRD §5.8: "Support tag filters, relationship-type filters where applicable". `search:query` takes
`relationshipTypeIds` (up to 20); the search keeps nodes with at least one relationship of any
chosen type, at either end, combined with the tag filter. The Search view shows a **Has a
relationship** row of chips for the types in use. Tests: `sqlite-search-index.test.ts` block
"relationship-type filter" (either end; any of several types; combined with tags; an unused type;
a type from another workspace), and the packaged bridge check "relationships, wikilinks, backlinks
and search through the bridge" (the filter keeps the related note and drops it for another type).
