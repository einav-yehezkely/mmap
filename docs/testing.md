# Testing

mmap uses [Vitest](https://vitest.dev) for every automated test, plus a smoke test that runs inside
the packaged app. This page lists the test layers, how to run them, the rules every change must
follow, and what is not automated yet.

## Test projects

`vitest.config.ts` at the root defines one Vitest project per package plus a repository-level
architecture project. All run on plain Node 24; none of them start Electron. Tests run in the
`node` environment; a file that needs a DOM opts in with a `// @vitest-environment jsdom` comment
(currently `editor-schema.test.ts` and `wikilink-node.test.ts`; `map-model.test.ts`,
`graph-model.test.ts`, `graph-layout.test.ts`, `timeline-model.test.ts`,
`timeline-axis.test.ts` and `home-model.test.ts` need no DOM).

The total on `main` (2026-10-28) is **1,183 passing tests in 69 files, plus two benchmark
files (4 tests) that are skipped by default**: 71 files, 1,187 tests. The skipped files are the
[search benchmark](#search-benchmark) (`storage-sqlite`) and the
[portability benchmark](#portability-benchmark) (`desktop`). Earlier totals: Phase 4 ended with
1,053 in 57 files (1,007 in 54 before the timeline redesign), Phase 3 with 882 in 45 files, Phase 2
with 736 before its review follow-ups, Phase 1 with 570, Phase 0 with 112. Run `npx vitest run` to
see the current numbers; the counts show the balance between layers and are not a target.

## Running tests

| Command                                                 | Runs                                                                             |
| ------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `npm test`                                              | Every project once                                                               |
| `npm run test:watch`                                    | Every project in watch mode                                                      |
| `npx vitest run --project storage-sqlite`               | One project (`domain`, `contracts`, `storage-sqlite`, `desktop`, `architecture`) |
| `npx vitest run packages/storage-sqlite/src/migrations` | Tests under one path                                                             |
| `npx vitest run -t "stale lock"`                        | Tests whose name matches                                                         |
| `npm run verify`                                        | Format, lint, typecheck, tests and build                                         |
| `npm run smoke:packaged`                                | The packaged smoke test (see below)                                              |

Storage tests create files named `mmap-test-*` in the OS temp directory; workspace, attachment and
acceptance tests create their own temporary folders. All of them are deleted when each test
finishes.

## Rules

These follow PRD §10.6 and §11 and the cross-cutting rules in the implementation plan.

- **Real SQLite, not mocks.** Anything involving SQL, transactions, constraints, triggers, FTS5 or
  migrations is tested against a real database file. Use
  `packages/storage-sqlite/src/test-support/temporary-database.ts`: `openMigratedTemporaryDatabase()`
  gives a fully migrated file in a temp folder with a `dispose()` that cleans up; the `insert`
  helpers create minimal valid rows; `nextTestId()` returns deterministic canonical UUIDs;
  `FIXED_TIME` is a valid UTC timestamp. Use a file rather than `:memory:` so WAL behaviour is
  real. Domain services are tested in `packages/storage-sqlite` for this reason: they run on the
  real repositories.
- **Real files for file handling.** The attachment store and the workspace manager are tested on
  real temporary folders; the store tests create Windows junctions for the escape cases.
- **Mock only external boundaries.** Fakes are fine for things outside the unit under test: the
  native dialogs and OS opener passed to the attachment and workspace services, `isProcessAlive`
  in the lock environment, the service passed to an IPC handler, the failure logger. Inject clocks,
  ID generators and timers instead of mocking globals where possible; the autosave tests use
  Vitest fake timers.
- **Every bug fix gets a regression test** that fails without the fix. Phase 1 examples: a
  follow-up autosave was never scheduled for edits made during an in-flight save; `list()` threw
  synchronously on an invalid cursor instead of rejecting.
- **Negative and security tests are required.** For each rule, test that the violation is
  rejected, not only that valid input works. Every IPC channel needs tests for untrusted senders,
  malformed and hostile payloads, and response leakage. Path handling needs traversal, encoded
  separator, drive-letter and symlink or junction cases.
- **Test the database's second line of defense separately** from the domain rule. Services
  enforce invariants first; schema tests prove the database still rejects a violation if a
  service has a bug (for example cross-workspace tagging and unsafe attachment paths).
- **Keep domain tests free of infrastructure.** The architecture test will fail if a domain test
  file imports Node built-ins, SQLite or Electron, because it scans all files under
  `packages/domain/src`.

### Recommended habit: check that a test can fail

A passing test only helps if it would fail when the rule breaks. When you add a test for a rule,
break the rule on purpose (comment out the revision check, accept `javascript:` links, skip the
lock check), run the test, confirm it fails for the right reason, and restore the code. This
is a manual practice, not an automated mutation-testing tool; nothing in CI does it for you.

## Search benchmark

`packages/storage-sqlite/src/search/search.benchmark.test.ts` measures `SqliteSearchIndex` and,
since Phase 4, `SqliteGraphQuery` on the PRD §9 dataset size. It is skipped unless `MMAP_BENCHMARK=1` is set, because building the data
takes a while. Run it from the repository root (Git Bash syntax):

```sh
MMAP_BENCHMARK=1 npx vitest run --project storage-sqlite search.benchmark --silent=false
```

What it does:

- Builds a fresh migrated database with 10,000 nodes, 30,000 relationships and 200 tags, generated
  by a seeded pseudo-random generator so every run measures the same data. Rows are inserted with
  SQL directly, not through the services. Word frequencies are skewed, and the vocabulary
  includes Hebrew words.
- Runs 250 searches: single words, second pages, two words, prefixes, tag filters, Hebrew words
  and queries with no hits. Runs 220 title lookups, a third of them substrings from the middle of
  a title (the slower, non-prefix path).
- Prints p50, p95 and maximum for all searches, per search workload and for title lookup, and
  fails if search p95 is 500 ms or more
  (PRD §9) or title lookup p95 is 100 ms or more (a budget for interactive typing). Each search
  asks for 20 results.
- Graph (Phase 4): 20 overviews at the PRD limits (1,000 nodes, 3,000 edges), 5 rounds of four
  filter sets (none, one tag, two relationship types, one word of text), all with the note-link
  layer on; the unfiltered overview must return 1,000 nodes with a total of 10,000. Then 50
  neighborhood expansions (up to 200 neighbors): the best-connected node and 49 others. Fails if
  the overview p95 is 1 second or more (well inside the PRD §9 budget of 3 seconds for rendering
  the initial graph) or the neighborhood p95 is 300 ms or more. The header of
  `sqlite-graph-query.ts` records why the queries are simple scans (see
  [architecture.md](architecture.md#simple-scans-ranking-in-typescript)); the slower SQL-heavy
  versions it mentions (about 600 ms, and minutes) were timed during development with temporary
  instrumentation, not by this benchmark.

Results measured on 2026-10-27 on a developer machine (not the reference machine):

| Operation          | Calls | p50    | p95    | Max    |
| ------------------ | ----- | ------ | ------ | ------ |
| Search             | 250   | 3.3 ms | 50 ms  | 63 ms  |
| Title lookup       | 220   | 25 ms  | 31 ms  | 41 ms  |
| Graph overview     | 20    | 191 ms | 267 ms | 301 ms |
| Graph neighborhood | 50    | 214 ms | 226 ms | 235 ms |

The graph rows come from a later run of the redesigned graph query (with map memberships),
measured while other processes loaded the machine: in the same run search p95 doubled from
52 ms to 101 ms, so the graph numbers are upper bounds. The dataset has no mind maps, so map
membership adds only an empty scan of `map_placements` here.

Run again on 2026-10-27 on branch `phase-5-portability` (developer machine, p95 only):

| Operation          | p95     |
| ------------------ | ------- |
| Search             | 70.8 ms |
| Title lookup       | 32.8 ms |
| Graph overview     | 240 ms  |
| Graph neighborhood | 190 ms  |

Limits of this measurement: it runs on system Node, calls the index directly (no IPC, no
renderer), on a developer computer rather than the documented four-core, 16 GB, SSD reference
machine, and not with the installed build. The PRD target is met with a wide margin here, but it
still has to be confirmed on the reference machine with the installed app. The graph rows measure
loading the data only; rendering is measured by the packaged smoke check "1,000-node graph
renders within 3 seconds".

## Portability benchmark

`apps/desktop/src/main/portability/portability.benchmark.test.ts` measures backup, restore,
export and import on the PRD §9 validation dataset, and records the restore time that PRD §9 and
[ADR-0006](adr/0006-backup-policy.md) require. It is skipped unless `MMAP_BENCHMARK=1` is set.
Run it from the repository root (Git Bash syntax):

```sh
MMAP_BENCHMARK=1 npx vitest run --project desktop portability.benchmark --silent=false
```

In PowerShell: `$env:MMAP_BENCHMARK = '1'; npx vitest run --project desktop portability.benchmark --silent=false`.

What it does:

- Starts real `WorkspaceManager` instances on temporary profiles and writes the dataset with bulk
  SQL inside the open workspace (the services would take far longer for this many records):
  10,000 nodes, 30,000 relationships, 100 maps with 50 placements each plus one with 500, 10,000
  timeline events and 50 attachments of 200 KB. The data comes from a seeded pseudo-random
  generator, so every run measures the same data.
- Times the real code paths: a backup with `BackupService`, then a restore of the open workspace
  from it (which includes the safety backup), and checks that the restored workspace has every
  node and attachment; fails if the restore takes 15 minutes or more (PRD §9). Then a ZIP export,
  and an import preview and apply into a second, empty workspace, which must end with 10,000
  nodes.

Results measured on 2026-10-27 on a developer machine with system Node (not the reference machine):

| Operation                                     | Time  |
| --------------------------------------------- | ----- |
| Building the dataset                          | 2.4 s |
| Backup                                        | 1.6 s |
| Restore, including the safety backup          | 2.7 s |
| ZIP export                                    | 0.9 s |
| ZIP import: preview (validation and planning) | 0.6 s |
| ZIP import: apply                             | 8.3 s |

The import apply took 23.9 s before the note-reference fix in this phase: every imported note
rebuilt its references with a `DELETE` that scanned all references of the workspace. The fix and
its query-plan regression test are described in
[data-model.md](data-model.md#note_references-notereference). These benchmark numbers come from
running the import in-process under Vitest. In the app the records are written in a worker
thread; measured once in the packaged app with 5,000 nodes, the import took 4.2 s (3.8 s
in-process) and the longest stall of the main process's event loop was 19 ms (3.8 s
in-process).

## Accessibility check

The packaged smoke check "primary views pass automated WCAG 2.2 AA checks"
(`apps/desktop/src/main/smoke-accessibility.ts`) injects axe-core 4.14.0 into the renderer of the
packaged app and runs the rules tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa`
on nine views, opened by clicking the real navigation: Home; the New node dialog; the Library with
the node editor open (a new node); Mind Maps; the Knowledge Graph and its List tab; the Timeline
and its List tab; and Settings. Every view is scanned twice, in the light and in the dark theme
(`nativeTheme.themeSource`); after each switch the window is reloaded and the check waits until
`prefers-color-scheme` matches, because colors already on screen lag behind a live switch. Because it runs in the real app with the production theme, color contrast is
computed from the actual colors. axe-core is a development dependency and is not shipped:
`smoke-packaged.mjs` resolves `axe-core/axe.min.js` and passes its path with `--smoke-axe=<path>`.

All views pass in both themes. The first run found one violation, an `aria-controls` attribute on
the graph's **Find in graph** box that pointed at an element that was not rendered; it was fixed.
Later, CI (which runs in the light theme) found the amber "partial results" warnings below 4.5:1
on white, which local runs in the dark theme had missed; they now use `amber-700`, and the
two-theme scan exists so that such a problem shows up locally too.

Automated rules find only part of the accessibility problems. Not yet done, and required before
release (PRD §6, acceptance criterion 14), is a manual pass of the primary flows:

- Keyboard only: reach and operate every control in the order shown, with a visible focus ring;
  create and edit a node, add a tag, a link and a relationship; use the map outline; use the graph
  and timeline List tabs; open and close every dialog with Escape, with focus returning to where
  it was.
- Screen reader (for example NVDA or Narrator): headings and landmarks of each view, names of
  icon buttons, the map outline's tree, timeline markers, live status messages (save state,
  backups, export and import), and error messages.
- Known gap: the knowledge graph canvas itself is not keyboard-operable; the List tab is the
  alternative.

## Security tests for archives and backups

Imported archives and backup folders are untrusted input (PRD §8, §11). The tests that treat
them as hostile:

- `archive-security.test.ts` builds malicious archives on the fly and checks that each is
  rejected with the right code before anything changes: traversal (`../`, nested
  `attachments/../../`),
  absolute and drive-letter paths, backslashes, control characters, symbolic links, names that
  repeat in another letter case, files outside the layout, a zip bomb (rejected by its declared
  size before inflating), an entry that inflates to more than it declares, too many entries, a
  non-ZIP file, a newer format, a checksum mismatch, unknown fields, inconsistent data and hostile
  note content. It also checks that executables are left out by their bytes even under an
  innocent name and type, and that copied files are removed when a later attachment fails.
- `import-plan.test.ts` checks the consistency rules of the planner (repeated IDs, missing
  references, self and duplicate relationships, cycles, invalid dates and fields).
- `backup-service.test.ts` checks that a backup manifest whose stored paths would leave the
  restored workspace folder is rejected, that a folder that is not a backup is rejected, and that
  a damaged snapshot leaves the open workspace unchanged.
- `catalogue.test.ts` sends hostile payloads (paths, SQL text, unexpected properties) to every
  channel, the `transfer:*` and `backups:*` channels included; none of them accepts a path.
